# opnDossier v1.7.3 — Reporting what the config actually says

v1.7.3 is a patch release, and almost all of it is one class of defect: the tool quietly saying less than the configuration contained. An audit reported a firewall rule matching all traffic as compliant. `diff` answered "No changes detected" for a port forward retargeted to a different internal host. Values that parsed correctly never reached the report. Two credential fields were emitted in cleartext by `sanitize`. Every one of these failed silently — no error, no warning, exit 0.

It also fixes three cases where a command failed outright on real vendor input: `sanitize` on the charset OPNsense actually writes, device detection on a Windows-1252 config, and the published GitHub Action's `output` input.

## Breaking changes

Two JSON/YAML key changes in `pkg/schema`, both accepted under the vendor-tracking carve-out in [`docs/development/public-api.md`](./docs/development/public-api.md):

- **`schema.SysctlItem` no longer emits `item`.** The field existed only to absorb a mis-bound `<sysctl>` element and became unreachable once that binding was corrected.
- **`schema.DhcpdInterface.FailoverPeerIP` (pfSense) now emits `failoverPeerIp`**, not `failoverPeerIP`, matching `pkg/model` and the Title-case acronym convention used by the rest of that struct.

The stability-tracked packages are unaffected: the `pkg/model`, `pkg/parser`, `pkg/parser/opnsense` and `pkg/parser/pfsense` API snapshots are additive only. ([#822](https://github.com/EvilBit-Labs/opnDossier/pull/822))

## Fixed

**A pass rule matching all traffic was reported compliant.** An endpoint that matches every host reaches `common.RuleEndpoint.Address` as one of four values — `any`, any other casing of it, the empty string when the element is omitted, or a wildcard CIDR like `0.0.0.0/0`. Sixteen call sites compared it against the `"any"` literal with a bare `==`, so three of the four read as a specific host. `FIREWALL-022` and `FIREWALL-023`, the two highest-severity rule checks, passed a WAN pass rule written any of those ways. `testdata/gateway_groups_test.xml` already contains a `<rule>` with no `<source>`, so the empty-string spelling was reachable on shipped fixture data rather than only in theory. The codebase also disagreed with itself — the overlap engine already treated an empty address as any, so two parts of the same audit answered differently about the same rule. Detection now routes through shared `IsAnyEndpoint` / `IsAnyAddress` / `IsAnyPort` / `IsAnyProtocol` / `IsWideOpenPassRule` predicates across the firewall, SANS and STIG checks, red-mode observations, and `DetectSecurityIssues`. ([#811](https://github.com/EvilBit-Labs/opnDossier/pull/811))

**`diff` was silent about the changes an operator most needs to see.** On the shipped pfSense fixture, flipping a firewall rule from pass to block reported nothing, and so did redirecting a port forward to a different internal host. Four independent gaps: rules were paired by UUID, which pfSense never writes and 10 of the 13 shipped fixtures lack, with a fallback that compared only the rule *count*; `--detect-order` had the same dependency, so a documented flag silently found nothing on pfSense; NAT rules were compared by count alone in both directions, which was the path every real config took; and the equality helpers had drifted from the models, covering 7 of `common.FirewallRule`'s 33 fields and 5 of `common.User`'s 7. A field missing from those helpers does not weaken the diff entry — it removes it, so the diff stayed quiet about a rule's direction being reversed, its gateway redirected, its state type weakened, its logging turned off, and about a user's UID changing or an API credential being added, rotated or removed. Matching now goes through one pairer: by vendor identity where one exists, then by exact content so unchanged rules anchor in place, then by similarity so a deletion cannot shift an edit onto its neighbor. ([#812](https://github.com/EvilBit-Labs/opnDossier/pull/812))

**Configured values reached the parser and never reached the report.** Nine vendor elements either decoded into something smaller than the file contained or were discarded at the converter boundary. Outbound NAT rules record their destination port in a `<dstport>` sibling that the model did not carry, so the two ISAKMP rules in the shipped pfSense fixture read as matching every port instead of 500. OPNsense modelled group members and privileges as scalars and had no user privileges at all, so a three-member group read as one member. OpenVPN `crypto`, `digest` and `ncp-ciphers` were absent from both client and server schemas, so cipher strength never reached a report. Firewall rule `tag` and `tagged` were dropped on both vendors, so the mark-then-match pairs that implement egress policy read as unconditional rules. The pfSense converter never built the advanced DHCP structures at all. Two related fixes belong to the same class: only the *last* of each repeated `<dnsserver>` survived decoding, so DHCP scopes advertising two resolvers reported one ([#799](https://github.com/EvilBit-Labs/opnDossier/pull/799)); and eight element types the vendor writes as empty placeholders — `route`, `bridged`, `ppp`, `gif`, `gre`, `lagg`, `vip`, `vlan` — became phantom entries, so a firewall with no tunnels or LAGG bonds reported one of each ([#789](https://github.com/EvilBit-Labs/opnDossier/pull/789)). Recovering the dropped privileges also fixed the control that reads them: `FIREWALL-018` audited clean on exactly the configs it exists to catch, because the converters join repeated `<priv>` elements with `", "` and the check split on a bare `","` without trimming. ([#822](https://github.com/EvilBit-Labs/opnDossier/pull/822))

**Two credential fields were emitted verbatim by `sanitize`.** A bare `<ldap_bindpw>` — one outside an `<authserver>` parent — matched no rule at all and was emitted in cleartext in every mode; the note above the rule table claimed it fell through to the password rule, but the field contains none of that rule's patterns. `<ddnsdomainkey>`, the shared HMAC secret authorizing pfSense DHCP dynamic-DNS updates, was emitted in cleartext in moderate and minimal mode. Aggressive mode redacted it only by accident, via the `domain` substring on the hostname rule, filing an HMAC key under the hostname namespace. Both are now redacted in every mode, the TSIG key as private-key material. Sanitizer output is byte-identical on every shipped fixture in every other respect. ([#798](https://github.com/EvilBit-Labs/opnDossier/pull/798))

**Aggressive mode corrupted the DHCP metadata the audit engine reads.** The same `domain` substring claimed three TSIG *metadata* fields — `ddnsdomainkeyname`, `ddnsdomainkeyalgorithm` and `ddnsdomainalgorithm` — and a field-name match redacts unconditionally, so the literal `hmac-md5` an audit needs to see was rewritten to `host-001.example.com`. Moderate and minimal were correct, leaving the highest-privacy mode as the only one destroying audit-relevant data. Rules gain `FieldExclusions`, anchored on the terminal path segment, so these three fields are no longer claimed by name. The value-detector pass still runs, so a genuinely hostname-shaped value stored in one of them is still redacted. Fixes [#818](https://github.com/EvilBit-Labs/opnDossier/issues/818). ([#821](https://github.com/EvilBit-Labs/opnDossier/pull/821))

**`sanitize` failed outright on the charset OPNsense writes.** OPNsense emits `<?xml version='1.0' encoding='us-ascii'?>`, and `sanitize` exited 1 with `xml: encoding "us-ascii" declared but Decoder.CharsetReader is nil`, producing nothing. Two shipped fixtures declare it; ISO-8859-1 and Windows-1252 configs failed identically, and all three are listed as supported on five documentation pages. Separately, device detection carried its own stricter charset reader, so a Windows-1252 config was rejected with a misleading `unsupported device type: no root XML element found` — as were the spellings the shared reader normalizes (`latin1`, `cp1252`, `ISO-8859-1:1987`, and others). Both paths now use one reader, so the supported set is defined in a single place and the documentation describes it accurately. Sanitized output is always UTF-8, and the declaration is rewritten to match the bytes actually written; UTF-8 and declaration-less inputs are byte-identical to before. ([#795](https://github.com/EvilBit-Labs/opnDossier/pull/795), [#796](https://github.com/EvilBit-Labs/opnDossier/pull/796))

**The GitHub Action's `output` input never worked.** The published image runs as `USER 65532:65532` and the composite action never told the container which uid to use, so it could not write into a runner workspace owned by uid 1001. Every invocation using the documented `output` input failed with `permission denied`, for `convert`, `audit` and `sanitize` alike. Runs that only wrote to stdout were unaffected, which is why it shipped. The action now passes `--user "$(id -u):$(id -g)"`; the image keeps its non-root default for bare `docker run`. ([#794](https://github.com/EvilBit-Labs/opnDossier/pull/794))

## Also in this release

- **`sanitize` could emit a document that no longer parses**, with exit 0. A comment ending in a hyphen came back as `<!--migrated 2024--->`, which XML 1.0 forbids, and every multi-line comment was flattened onto one line. Redaction now runs in place per token, so original spacing and newlines survive, and the fuzz target enforces that accepted output re-parses rather than only that the sanitizer does not panic. ([#797](https://github.com/EvilBit-Labs/opnDossier/pull/797))
- **An oversized config was reported as corrupt.** An 11 MB `config.xml` produced `XML syntax error on line 1: unexpected EOF`, sending the operator after the wrong problem. The error now names the size cap and its value while preserving the underlying decode error, and the 10 MB limit is still enforced to the byte. ([#800](https://github.com/EvilBit-Labs/opnDossier/pull/800))
- **`--version` reported `unknown (built from source)` in tagged builds** while the `version` subcommand reported the real version — and `--version` is the surface automation and package managers read. Both now read the injected values, and `--version` carries the commit. Two ldflags targeting symbols that did not exist were removed. ([#801](https://github.com/EvilBit-Labs/opnDossier/pull/801))
- **A security claim in the threat model was corrected.** The CWE-312 row stated that JSON and YAML serialization redacts certificate private keys, CA private keys and SNMP community strings unconditionally. It does not: `ToJSON` and `ToYAML` take a `redact` parameter bound to `--redact`, which defaults to false, so a plain `convert --format json` writes those values in cleartext. The row now separates the unconditional control (`sanitize`) from the opt-in one, and is marked partially mitigated. ([#803](https://github.com/EvilBit-Labs/opnDossier/pull/803))
- **The race detector no longer runs on GitHub.** The instrumented suite was slow and contended enough on shared runners to red-light a clean tree and green a rerun with no code change, which taught contributors to re-run it rather than read it. It still runs locally via `just test-race`, and `just ci-check` includes it; the `forbidigo` lint rule that catches the underlying `t.Parallel()` hazard in `cmd/` is unchanged. ([#790](https://github.com/EvilBit-Labs/opnDossier/pull/790))
- An unreachable domain mapper removed from the sanitizer ([#791](https://github.com/EvilBit-Labs/opnDossier/pull/791)), the golangci-lint pin aligned with `mise.toml` to resolve a local/CI skew ([#813](https://github.com/EvilBit-Labs/opnDossier/pull/813), [#819](https://github.com/EvilBit-Labs/opnDossier/pull/819)), documentation binary-name contradictions, nav gaps and duplicate pages fixed ([#787](https://github.com/EvilBit-Labs/opnDossier/pull/787)), version references pointed at the current release ([#802](https://github.com/EvilBit-Labs/opnDossier/pull/802)), the solutions store refreshed against the current codebase ([#823](https://github.com/EvilBit-Labs/opnDossier/pull/823)), and routine dependency bumps.

## Upgrade notes

Upgrading is a drop-in replacement — no config changes and no CLI changes — but this release makes the tool report things it previously did not, so expect output to change.

**Audits may now fail where they previously passed.** `FIREWALL-022` and `FIREWALL-023` correctly fail wide-open WAN pass rules ([#811](https://github.com/EvilBit-Labs/opnDossier/pull/811)), and `FIREWALL-018` correctly fails groups and users holding excessive privileges ([#822](https://github.com/EvilBit-Labs/opnDossier/pull/822)). These are findings that were being missed, not new checks, and `audit` still exits 0 whether or not a control fails — so a pipeline reading the report rather than the exit status will see counts move. Review the new findings before assuming a regression.

**`diff` reports changes it previously missed.** Pass-to-block flips, retargeted port forwards, NAT rule content changes, and `--detect-order` on configs without rule UUIDs. Scripts that asserted on "No changes detected" will see new output.

**Exports change in both directions.** They now contain values that were previously absent (NAT destination ports, group and user privileges, OpenVPN cipher settings, firewall rule tags, advanced pfSense DHCP settings, every repeated `<dnsserver>`) and no longer contain phantom entries for unconfigured tunnels, LAGG bonds, VLANs, virtual IPs, PPP links, bridges and static routes ([#789](https://github.com/EvilBit-Labs/opnDossier/pull/789)). Golden files and snapshot tests will need regenerating.

**`common.DHCPScope.DNSServer` is deprecated in favor of `DNSServers`.** The scalar is still emitted and mirrors the first entry, so existing consumers keep working; it will be removed after the documented deprecation cycle. ([#799](https://github.com/EvilBit-Labs/opnDossier/pull/799))

**Sanitized output differs.** TSIG keys and bare `ldap_bindpw` values are now redacted in every mode, and aggressive mode no longer rewrites TSIG algorithm names as hostnames. Tooling that consumed the old output will need updating.

**GitHub Action users should re-pin to `v1.7.3`.** The `output` input did not work in any earlier release.
